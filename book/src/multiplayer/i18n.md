# i18n

The lobby's user-facing strings are funnelled through a small
`tr(Key)` shim at `open4x-lobby/src/components/i18n.rs`. Today
only `Locale::En` is wired; the structure is the seam for adding
a second language.

## Convention

In a Leptos view, replace any user-facing string literal with a
`tr(Key::...)` call:

```rust
use crate::components::i18n::{tr, Key};

view! {
    <h1>{tr(Key::LoginPageTitle)}</h1>
    <Btn>{tr(Key::LoginEmailSendButton)}</Btn>
}
```

The `Key` enum lives in the same module. Adding a new string is
two steps:

1. Add a variant to `Key`. Convention is `<screen>_<role>` —
   e.g. `OngoingFilterAll`, `WizardStepCivHeading`,
   `ProfileChangeAvatar`.
2. Add a match arm in `en()`.

The compiler enforces exhaustiveness: a missing arm fails to
compile, and adding a new locale (see below) won't let the build
through until you've translated every key.

### Templated strings

Use `{name}` placeholders in the English source, then
`.replace("{name}", &value)` at the call site:

```rust
// Key::LoginEmailSentTemplate ↦ "Magic link sent to {to}. Check your inbox."
let copy = tr(Key::LoginEmailSentTemplate).replace("{to}", &address);
```

Format strings (`{}` from `format!`) are *not* used because the
template needs to survive a translation pass intact, including
the placeholder names.

## Adding a second locale

When someone wants to translate the SPA:

1. Add a variant to `Locale` (e.g. `De`).
2. Provide a `Locale` value via `provide_context` at App root.
   Seed it from `navigator.language` or a per-account preference.
3. Update `tr_in` to dispatch on the locale:
   ```rust
   pub fn tr_in(locale: Locale, key: Key) -> &'static str {
       match locale {
           Locale::En => en(key),
           Locale::De => de(key),
       }
   }
   ```
4. Add a sibling `de(key)` function with a match arm per `Key`
   variant. The compiler refuses to build until every variant
   has a German translation.
5. Existing `tr(Key)` call sites stay as-is. They funnel through
   `Locale::default()` today; a follow-up can route them through
   the context'd locale via a new `tr_reactive(Key) -> Signal<&str>`
   helper.

## Why no library

Three concrete reasons:

1. **Wasm size.** `fluent` adds ~1 MB to the wasm bundle for
   features the lobby doesn't need (gender / plurals / context
   resolution). A `match` statement is byte-for-byte cheaper.
2. **Compile-time exhaustiveness.** Library-driven i18n typically
   uses a string key (`tr("login.signin")`) which fails at
   runtime when a translation is missing. The `Key` enum + match
   arms mean every translation gap is a compile error.
3. **Bundle-vs-fetch tradeoff.** Most candidates either bundle
   every locale into the wasm (dead weight on a cold cache) or
   require an XHR per language (cold-start latency). Match
   statements live in the wasm but only the active locale's
   strings are reachable, so dead-code elimination can prune
   the rest if we add `[cfg(feature = "lang-X")]` later.

The shim isn't a final answer. When the second language ships
the surface area to migrate is small (one module + the call
sites are already through `tr`), so swapping in a real library
later is a low-cost option if requirements grow.
